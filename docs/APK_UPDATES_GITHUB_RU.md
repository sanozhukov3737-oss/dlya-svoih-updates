# Обновления приложения через GitHub

## Первая установка клиента

Версия 0.3.114 добавляет скачивание APK и вызов системного установщика Android. Один раз соберите её на том же ПК, что и установленную 0.3.113, и установите поверх старой версии. Не удаляйте приложение.

```powershell
.\MAKE_APK.bat
explorer.exe ".\app\build\outputs\apk\debug"
```

Откройте «⋮ → Обновления». Вверху находится «Приложение», ниже — «Каталог». В уже опубликованном latest.json пока описан только каталог №147: надпись «Обновления APK ещё не опубликованы» ожидаема. Сборка нового APK и публикация описания нужны для каждого изменения интерфейса или кода; изменения только каталога остаются отдельными ZIP-обновлениями.

## Сохранение подписи

Текущий MAKE_APK.bat собирает debug APK, подписанный ключом данного ПК. GitHub должен использовать именно этот ключ. Не создавайте другой: Android не примет обновление поверх текущей установки. Клиент проверяет сертификат установленного приложения, сертификат скачанного APK, packageName, версии, минимальную версию Android, размер и SHA-256. Сам Android также проверяет подпись при установке.

На ПК в PowerShell из папки проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\copy_github_debug_key.ps1
```

Скрипт копирует ключ в буфер обмена, не выводит его и не сохраняет новый текстовый файл. Стандартный путь: `%USERPROFILE%\.android\debug.keystore`. При нестандартном расположении укажите путь через `-KeystorePath`; нужен ключ именно той сборки, которая установлена на телефоне.

В репозитории `sanozhukov3737-oss/dlya-svoih-updates` откройте Settings → Secrets and variables → Actions → New repository secret. Имя: `ANDROID_DEBUG_KEYSTORE_BASE64`. В Value вставьте содержимое буфера и сохраните. Ключ нельзя добавлять в файлы репозитория, сообщения или описание выпуска. `.gitignore` исключает keystore-файлы, keystore.properties, APK, ZIP и результаты сборки.

## Загрузка исходников

Для GitHub Actions нужны исходники проекта в корне того же репозитория, а не только ZIP-архив. В корне должны оказаться `app`, `gradle`, `tools`, `gradlew`, `build.gradle.kts` и `.github/workflows/build-apk.yml`. Файлы выпусков останутся на месте.

Если Git установлен, из распакованной папки проекта:

```powershell
git init
git branch -M main
git remote add origin https://github.com/sanozhukov3737-oss/dlya-svoih-updates.git
git add .
git commit -m "Add Android app and APK update workflow"
git pull origin main --allow-unrelated-histories --no-rebase
git push -u origin main
```

Это команды для нового распакованного проекта, ещё не связанного с Git. Если GitHub потребует вход, используйте его штатную авторизацию. При конфликте с изменёнными файлами репозитория не применяйте force push: сначала разрешите конфликт. На этом этапе исходники попадут в публичный репозиторий, ключ подписи — только в Actions Secret.

## Сборка и выпуск

В репозитории: Actions → Build and publish APK → Run workflow. Оставьте Tag пустым (получится `app-0.3.114`) и заполните описание изменений. Запуск вручную означает сборку и публикацию обычного выпуска после успешных проверок.

Сценарий восстанавливает существующий debug-ключ в стандартный путь Android, собирает APK, проверяет его через apksigner и apkanalyzer, читает последнее публичное описание каталога и добавляет поле `app`. После загрузки APK и latest.json публикует выпуск как latest. Ссылка на каталог остаётся привязана к его прежнему тегу: например catalog-147/catalog-147.zip. Загружать копию этого ZIP в каждый выпуск APK не требуется.

Если ключ отсутствует, подпись изменилась, versionCode не увеличен относительно предыдущего опубликованного APK или сборка упала, новый выпуск не публикуется. В случае ошибки завершающей публикации может остаться черновик: проверьте Releases и журнал Actions перед повторным запуском. Старое опубликованное обновление продолжает работать.

Первый выпуск APK 0.3.114 проверит подключение канала. На телефоне с той же версией будет «У вас актуальная версия приложения». Для следующего реального изменения кода нужна версия 0.3.115 и versionCode 119: клиент предложит её скачать, проверить и установить. Не меняйте ключ, applicationId или способ подписи между выпусками.

## На телефоне

«Проверить приложение» выполняет проверку вручную. Автоматическая проверка включена по умолчанию и выполняется при запуске не чаще раза в сутки; настройка «Проверять каталог и приложение при запуске» общая. При закрытом приложении отдельного фонового расписания нет.

После обнаружения новой версии: «Скачать приложение» → «Установить обновление». В первый раз Android может открыть настройки разрешения установки из «ДЛЯ СВОИХ»: включите разрешение и вернитесь. Затем подтвердите установку в системном окне. Если отказались или закрыли окно, можно повторно нажать установку. Скачанный APK и предложение сохраняются между запусками и проверяются повторно перед установкой. После установки скачанный файл очищается при следующем запуске.

## Следующие обновления каталога

Общий latest.json должен сохранять поле app последнего выпуска APK, иначе новый выпуск только каталога временно уберёт предложение APK. Для подготовки каталога используйте предыдущий опубликованный JSON:

```powershell
python .\tools\build_update_feed.py --pack .\catalog-148.zip --url "https://github.com/sanozhukov3737-oss/dlya-svoih-updates/releases/download/catalog-148/catalog-148.zip" --output .\latest.json --previous-feed .\latest-before.json --changes-file .\changes.txt
```

latest-before.json — сохранённое последнее описание с GitHub. minAppCode для каталога остаётся 116, пока формат каталога не требует новых возможностей. Поле app и версия APK меняются только при выпуске нового приложения. Старые клиенты 0.3.112/0.3.113 игнорируют поле app и продолжают получать каталог.
