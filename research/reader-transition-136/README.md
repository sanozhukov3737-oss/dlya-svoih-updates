# Перелистывание карточек 0.3.136: диагностика

21 октября 2026 года. Приложение 0.3.136 / versionCode 140, каталог 197.
Исследованный исходник: `c05e63305c53d0e4c92c9f8edd0a7c4076198ed7`.
Изменения этого этапа — только отчёт и воспроизводимая диагностика. Приложение,
данные и публичное обновление не изменены; сборки и Android-прогоны не запускались.

## Что обнаружено

При создании страницы `CardReaderPages` создаёт принадлежащий ей
`DetailViewModel`. Модель сначала получает версию каталога и место чтения,
затем подписывается на `GuideRepository.detail(id)`. Первый `Ready` зависит от
карточки, изображений, источников, избранного, стран, похожих карточек **и полного
списка кандидатов для сравнения**. Только после `Ready` интерфейс создаёт
`DetailHero` с запросом изображения.

Окно сравнения в этот момент может быть закрыто. Запрос `comparisonCards`
всё равно выполняется и возвращает до **193 превью** для одной карточки текущего
каталога. Он не загружает полные тексты кандидатов: облегчение из 0.3.135
сохранено. Старт отображения карточки, однако, продолжает зависеть от этого списка.

| Участок | Фактическое поведение | Вывод для следующего этапа |
|---|---|---|
| Список сравнения | Входит в общий `combine`, даже когда окно закрыто | Первый кандидат: загружать по открытию сравнения |
| Текст | Разбиение на абзацы уже выполняется на `Dispatchers.Default`; `article()` и `sections()` вызываются при композиции и запоминаются через `remember` | Работа в потоке интерфейса есть, но локальная проверка не даёт основания считать её основной задержкой |
| Фото | Локальный asset/файл через `AsyncImage`; запрос запоминается по пути; общий кеш ограничен 4–32 МиБ в зависимости от устройства | Подтверждённой ошибки загрузки не найдено. Время декодирования и попадания в кеш здесь не измерены |
| Перелистывание | Использует предварительную подготовку страниц самим pager; хранилище модели очищается при удалении страницы из композиции | Не увеличивать число полностью подготовленных страниц без проверки памяти |

## Выполненная проверка

`diagnose.py` открывает упакованную базу только для чтения и проверяет её SHA-256:
`a2cf495b7476e65a52d8f14b22fe737e812310c4c49ee4aa784afd27ab59e8b5`.
База содержит 1695 активных карточек. Медианный текст — 1009 символов,
максимальный — 3575. В метаданных 1595 изображений: ширина и высота не больше
1600 пикселей. Это проверка записанных размеров, а не декодирование файлов.

- Выполнены настоящие Java-методы `ReaderContent.article`,
  `ReaderNavigation.sections` и поиск с пустым запросом на всех 1695 текстах:
  8 прогревочных проходов, затем 15 измеряемых в перемешанном порядке.
  Распределение медиан по карточкам: **0,0067 мс**, p95 **0,011897 мс**,
  наибольшая медиана **0,035903 мс**. Разбиение текста, измерение шрифта,
  компоновка Compose и разбор отдельных видимых блоков исключены.
- Проверены настоящие SQL `relatedCards` и `comparisonCards` с семействами из
  `CardFamilies.relatedIds`: 48 карточек, включая представителя каждой пары
  раздел/категория, по 25 повторов после прогрева каждого запроса.
  Для категории из 194 карточек список сравнения содержит 193 строки;
  медианы двух проверенных представителей — **1,60 и 1,87 мс**.
  Соседний запрос похожих карточек возвращает максимум 12 строк.
- Использованы хост x86_64, OpenJDK 17 и SQLite 3.53.1. SQL включает получение
  строк через Python, но не преобразование Room и планирование Android.

Исходные результаты и ограничения: [measurements.json](measurements.json).
Воспроизведение на указанном исходнике с Python и JDK 17:

```sh
python research/reader-transition-136/diagnose.py
```

Эти времена описывают прогретые операции на хосте. Они **не измеряют время
перелистывания на телефоне**, не определяют главный источник задержки в Android
и не доказывают ускорение будущей правки. Старые замеры прокрутки 0.3.136 также
не являются сравнением перехода между карточками до/после изменения.

## Предложение для следующего этапа

Одна правка: вынести полный список кандидатов сравнения из условия готовности
карточки и запрашивать его при открытии окна. Сохранить возможность открыть
сравнение для подходящей категории; предусмотреть загрузку, ошибку, повтор и
пустой список. Не менять порядок карточек и восстановление чтения.

До заявления об ускорении измерить одинаковые переходы на одной версии Android
и одном устройстве/эмуляторе: от начала перехода до готовности страницы и первого
фото, отдельно первый и повторный проход, плюс кадры и память. Фото из локального
кеша и заново декодированные фото учитывать отдельно. Если выигрыш не подтвердится,
не выдавать устранённую зависимость за найденную причину рывков.
